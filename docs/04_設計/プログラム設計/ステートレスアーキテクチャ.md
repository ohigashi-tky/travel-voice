# ステートレスアーキテクチャ解説

## 📚 基本概念

**ステートレスアーキテクチャ**とは、サーバーがクライアントの状態（セッション情報）を保持しない設計パターンです。

### 🔍 ステートフル vs ステートレス

#### ❌ ステートフル（状態保持あり）
```php
// サーバーがユーザーセッションを記憶
class StatefulController 
{
    private $userSession; // サーバー側で状態保持
    
    public function getData() 
    {
        // セッションから状態を取得
        if ($this->userSession->isLoggedIn()) {
            return $this->getPrivateData();
        }
        return response()->json(['error' => 'Unauthorized'], 401);
    }
}

// 問題点
// - サーバーメモリ/データベースにセッション保存
// - スケールアウト時にセッション共有が必要
// - サーバークラッシュでセッション消失
```

#### ✅ ステートレス（状態保持なし）
```php
// サーバーはリクエストごとに認証
class StatelessController 
{
    public function getData(Request $request) 
    {
        // 毎回トークンで認証状態を確認
        $user = $this->authenticateFromToken($request->header('Authorization'));
        
        if ($user) {
            return $this->getPrivateData($user);
        }
        return response()->json(['error' => 'Unauthorized'], 401);
    }
    
    private function authenticateFromToken($token) 
    {
        // JWTトークンをデコードして認証
        return JWT::decode($token);
    }
}

// 利点
// - サーバー側で状態保持不要
// - どのサーバーでもリクエスト処理可能
// - サーバークラッシュしても影響なし
```

## 🌟 ステートレスの利点

### 1. **スケーラビリティ（水平スケーリング）**

#### ステートフルの問題
```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  Server A   │    │  Server B   │    │  Server C   │
│ ユーザー1の │    │             │    │             │
│ セッション  │    │             │    │             │
└─────────────┘    └─────────────┘    └─────────────┘

ユーザー1のリクエスト → Server B → セッション情報なし！❌
```

#### ステートレスの解決
```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  Server A   │    │  Server B   │    │  Server C   │
│ 状態保持なし │    │ 状態保持なし │    │ 状態保持なし │
└─────────────┘    └─────────────┘    └─────────────┘

ユーザー1（トークン付き） → どのサーバーでも処理可能 ✅
```

### 2. **障害耐性（Fault Tolerance）**

#### ステートフル
```php
// サーバークラッシュでセッション消失
Server A クラッシュ → ユーザーのログイン状態が消失 ❌
→ 再ログインが必要
→ 作業中データも消失の可能性
```

#### ステートレス
```php
// サーバークラッシュしても他サーバーで継続
Server A クラッシュ → Server B/C で継続処理 ✅
→ ユーザーは影響を受けない
→ シームレスな体験
```

### 3. **開発・運用のシンプルさ**

#### メモリ管理
```php
// ステートフル
// - セッションデータでメモリ圧迫
// - ガベージコレクション必要
// - メモリリーク監視

// ステートレス  
// - メモリ使用量一定
// - セッション管理不要
// - シンプルな監視
```

#### デバッグ
```php
// ステートフル
// - セッション状態に依存するバグ
// - 再現困難な状態依存エラー
// - 複雑なテストシナリオ

// ステートレス
// - リクエスト/レスポンスのみ
// - 決定論的な動作
// - 単純なテストケース
```

### 4. **キャッシュ効率**

```php
// ステートレス API レスポンス
GET /api/travel-spots
→ 同じリクエスト = 同じレスポンス
→ CDN/プロキシで効率的にキャッシュ可能 ✅

// ステートフル API レスポンス  
GET /api/user-specific-data
→ セッションにより結果が変わる
→ キャッシュ困難 ❌
```

## 🔧 完全ステートレス化の実装

### 1. JWT認証への移行

#### 現在の仕組み（Sanctum + Session）
```php
// ログイン時
$user = User::where('email', $email)->first();
$token = $user->createToken('auth-token')->plainTextToken;

// 認証時  
Route::middleware('auth:sanctum') // データベースでトークン確認
```

#### 推奨の仕組み（Pure JWT）
```php
// JWT Helper クラス
class JWTHelper 
{
    public static function generateToken(User $user): string 
    {
        $payload = [
            'user_id' => $user->id,
            'email' => $user->email,
            'iat' => time(),
            'exp' => time() + (60 * 60 * 24), // 24時間
        ];
        
        return JWT::encode($payload, config('app.key'), 'HS256');
    }
    
    public static function validateToken(string $token): ?User 
    {
        try {
            $payload = JWT::decode($token, new Key(config('app.key'), 'HS256'));
            return User::find($payload->user_id);
        } catch (\Exception $e) {
            return null;
        }
    }
}

// AuthController での使用
class AuthController extends Controller
{
    public function login(Request $request) 
    {
        $user = User::where('email', $request->email)->first();
        
        if ($user && Hash::check($request->password, $user->password)) {
            $token = JWTHelper::generateToken($user);
            
            return response()->json([
                'access_token' => $token,
                'token_type' => 'Bearer',
                'expires_in' => 86400,
            ]);
        }
        
        return response()->json(['error' => 'Unauthorized'], 401);
    }
}

// ミドルウェア
class JWTMiddleware
{
    public function handle(Request $request, Closure $next)
    {
        $token = $request->bearerToken();
        
        if (!$token) {
            return response()->json(['error' => 'Token required'], 401);
        }
        
        $user = JWTHelper::validateToken($token);
        
        if (!$user) {
            return response()->json(['error' => 'Invalid token'], 401);
        }
        
        // リクエストにユーザー情報を設定
        $request->merge(['authenticated_user' => $user]);
        
        return $next($request);
    }
}
```

### 3. フロントエンド対応

#### Nuxt.js でのトークン管理
```typescript
// stores/auth.ts
export const useAuthStore = defineStore('auth', {
  state: () => ({
    token: null as string | null,
    user: null as User | null,
  }),

  actions: {
    async login(credentials: LoginCredentials) {
      const response = await $fetch('/api/login', {
        method: 'POST',
        body: credentials,
      });
      
      this.token = response.access_token;
      this.user = response.user;
      
      // ローカルストレージに保存
      localStorage.setItem('auth_token', this.token);
    },

    async logout() {
      this.token = null;
      this.user = null;
      localStorage.removeItem('auth_token');
    },

    // ページリロード時にトークンを復元
    restoreToken() {
      const token = localStorage.getItem('auth_token');
      if (token) {
        this.token = token;
        // トークンの有効性チェック
        this.validateToken();
      }
    },
  },
});

// API呼び出し時の自動ヘッダー設定
// plugins/api.client.ts
export default defineNuxtPlugin(() => {
  const authStore = useAuthStore();
  
  $fetch.create({
    onRequest({ request, options }) {
      if (authStore.token) {
        options.headers = {
          ...options.headers,
          Authorization: `Bearer ${authStore.token}`,
        };
      }
    },
  });
});
```
